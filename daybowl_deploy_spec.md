# DayBowl — деплой на GitHub Pages і збереження даних

Nov 21, 2026 · @Roman

## Мета і рішення

**Рішення:** публікуємо DayBowl як статичний PWA на GitHub Pages (`https://romanhrytsko.github.io/daybowl/`). Дані залишаються в IndexedDB браузера, як і зараз. Поверх цього додаємо три речі: запит на постійне сховище, встановлення як застосунок і страхувальні резервні копії. Бекенд і акаунти не потрібні.

**Що має вийти:** ти один раз проходиш онбординг і далі щоразу відкриваєш застосунок з тими самими чашами, шаблонами і категоріями. Кожен push у `main` оновлює сайт і не чіпає даних.

**Чому так**

- Збереження вже працює: Dexie пише в IndexedDB, і дані живуть між запусками. Дані прив'язані до *origin*, тож `localhost:5173` і Pages — це два різні сховища. Стабільна адреса на Pages дасть одне постійне місце.
- GitHub Pages безкоштовний, але на плані Free працює лише з **публічним репозиторієм** ([GitHub Plans](https://docs.github.com/en/get-started/learning-about-github/githubs-plans)). Це ок: у репозиторії лише код, твої дані туди не потрапляють. Адресу сайту зможе відкрити будь-хто, але побачить лише власну порожню чашу.
- Синхронізація між пристроями — опційна фаза 2. Якщо застосунок потрібен лише на одному пристрої, вона не потрібна.

**Поза обсягом:** акаунти, серверна база, власний домен, доступ для інших людей.

## Поточний стан репозиторію

Майже все для деплою вже є; бракує `base` у Vite, workflow і кількох захисних механізмів для даних. Стан гілки `main` (`github.com/RomanHrytsko/daybowl`):

| Що | Зараз | Що треба |
| --- | --- | --- |
| Збірка | Vite 6 + React 19 + TS, `npm run build` → `dist/` | Додати `base: '/daybowl/'` |
| Роутинг | Хеш-маршрути `#/week/…` у `uiStore.ts` | Нічого: хеші працюють на Pages без 404-хаків |
| PWA | `vite-plugin-pwa`, `registerType: 'autoUpdate'`, manifest | Перевірити `scope` / `start_url` після зміни `base`; додати PNG-іконки 192/512 |
| Сховище | Dexie, база `daybowl`, схема `version(1)` | Запит `navigator.storage.persist()`, правила міграцій |
| Перший запуск | `seedIfEmpty()` + онбординг за `settings.onboardedAt` | Нічого: повторно не запускається |
| Резервна копія | Ручний експорт / імпорт JSON у Налаштуваннях | Нагадування + дата останньої копії |
| Категорії і шаблони | Створення, редагування, **архівація** | Додати справжнє видалення |
| CI / деплой | Немає `.github/workflows` | Додати workflow: тести → збірка → Pages |

Особливість `index.html`: іконка підключена як `/icon.svg`. Vite переписує абсолютні шляхи в `index.html` з урахуванням `base`, але це треба перевірити в `dist/index.html` після збірки.

## Збереження даних

Дані лежать у браузері, тому головна загроза — автоматичне очищення сховища браузером. Три рівні захисту нижче знімають цей ризик.

**Ризики, які закриваємо**

| Ризик | Коли спрацьовує | Захист |
| --- | --- | --- |
| Safari чистить сховище | У Safari (macOS і iOS) IndexedDB сайту видаляється після 7 днів використання Safari без відвідування сайту ([web.dev](https://web.dev/articles/storage-for-the-web)) | Встановити як застосунок: для Home Screen / Dock-застосунків лічильник окремий і скидається при кожному відкритті |
| Браузер звільняє місце | Мало вільного місця на диску | `navigator.storage.persist()` при старті, статус у Налаштуваннях |
| Ручне очищення даних сайтів | «Очистити історію», новий профіль, новий ноутбук | Регулярний експорт JSON з нагадуванням |
| Новий деплой ламає схему | Зміна `stores()` у `version(1)` замість нової версії | Правило міграцій і тест на нього |
| Зміна адреси сайту | Перейменування репозиторію, власний домен | Новий origin = порожнє сховище; спершу експорт, потім імпорт |

**Рівень 1. Постійне сховище** (`src/data/persistence.ts`)

```ts
export async function requestPersistence(): Promise<boolean> {
  if (!navigator.storage?.persist) return false;
  if (await navigator.storage.persisted()) return true;
  return navigator.storage.persist();
}
```

- Викликати в `App` після `seedIfEmpty()` при **кожному** запуску (WebKit не запам'ятовує відмову назавжди).
- У Налаштуваннях показати рядок: «Сховище: постійне ✓» або «браузер може очистити — встанови як застосунок» + `navigator.storage.estimate()` (скільки зайнято).

**Рівень 2. Встановлення як застосунок**

- macOS: Chrome / Edge — іконка «Встановити» в адресному рядку; Safari — File → Add to Dock.
- iPhone: Safari → Поділитися → «На початковий екран».
- **Важливо:** на iOS встановлений застосунок має окреме сховище, спільного з Safari-вкладкою немає ([web.dev](https://web.dev/articles/storage-for-the-web)). Онбординг треба проходити вже в встановленому застосунку.
- У застосунку: якщо `display-mode` не `standalone`, показувати ненав'язливу підказку «Встанови, щоб дані не зникли», яку можна закрити. Закриття зберігати в `settings.installHintDismissedAt`.

**Рівень 3. Резервна копія з нагадуванням**

- Нове поле `Settings.lastBackupAt?: string`; оновлюється після `downloadBackup`. Поле опційне, тож міграція схеми не потрібна.
- Якщо копії не було понад 7 днів і є хоча б одна справа, на екрані Тиждень з'являється м'який банер «Остання копія N днів тому» з кнопкою «Зберегти копію».
- У Налаштуваннях показувати дату останньої копії.
- Копію зберігати в iCloud Drive / Google Drive, щоб вона пережила втрату ноутбука.

**Правило міграцій Dexie** (додати коментарем у `db.ts` і в README)

1. `version(1).stores({...})` більше ніколи не змінюється.
2. Новий індекс або таблиця — це `version(2).stores({...}).upgrade(tx => ...)`.
3. Нові неіндексовані поля робимо опційними; версію схеми не піднімаємо.
4. Тест: база, створена схемою v1 з даними, відкривається поточною `DaybowlDB` без втрат (`fake-indexeddb` вже є в залежностях).
5. Перед деплоєм із зміною схеми — експорт даних.

**Видалення типів справ** (зараз є лише архівація)

- **Шаблон:** видаляється фізично. Вже створені справи залишаються: вони мають власні `title`, `categoryId`, `minutes`. Майбутні повтори перестають генеруватися. Перед видаленням — підтвердження.
- **Категорія без справ і шаблонів:** видаляється фізично.
- **Категорія, яка вже використовується:** діалог з двома варіантами: «Архівувати» (історія збережена) або «Перенести в іншу категорію і видалити». Другий варіант виконується однією транзакцією по `activities` + `templates` + `categories`.

**Фаза 2 (опційно): синхронізація через приватний Gist**

Потрібна лише для одних даних на ноутбуці й телефоні або для автоматичної хмарної копії без ручного експорту. Лишається в екосистемі GitHub і не потребує бекенду.

- У Налаштуваннях вставляєш GitHub-токен з єдиним scope `gist`. Токен зберігається локально, до репозиторію не потрапляє.
- Застосунок створює приватний Gist `daybowl-backup.json` у тому ж форматі `Backup`, що й експорт.
- **Push:** через 30 с після останньої зміни (debounce на Dexie `hooks`) і при `visibilitychange → hidden`.
- **Pull:** при старті. Якщо `exportedAt` у Gist новіший за локальний `lastSyncedAt` і локальних змін немає, робимо імпорт. Якщо зміни є з обох боків — діалог «Взяти з хмари / Лишити локальні». Для одного користувача цього достатньо, позаписне злиття не потрібне.
- Ревізії Gist дають історію версій безкоштовно: будь-яку стару копію можна відновити.
- Ризик: токен у `localStorage` доступний будь-якому JS на `romanhrytsko.github.io`. Для особистого застосунку без сторонніх скриптів це прийнятно, але токен завжди тільки зі scope `gist`.

## Деплой на GitHub Pages

Деплой робить GitHub Actions при кожному push у `main`: тести → збірка → публікація. Коли тести падають, сайт не оновлюється.

**1. Vite: `base`** (`vite.config.ts`)

```ts
export default defineConfig(({ command }) => ({
  base: command === 'build' ? '/daybowl/' : '/',
  plugins: [ /* без змін */ ],
  // test: { ... } без змін
}));
```

- У dev-режимі лишається `/`, локальна розробка не змінюється.
- `vite-plugin-pwa` бере `scope` і `start_url` з `base`. Перевірити в `dist/manifest.webmanifest`, що обидва поля дорівнюють `/daybowl/`.
- Додати `public/icon-192.png` і `public/icon-512.png` до `manifest.icons`. Chrome для встановлення і iOS для іконки на екрані надійніше працюють з PNG. До `index.html` додати `<link rel="apple-touch-icon" href="/icon-192.png">`.

**2. Workflow** (`.github/workflows/deploy.yml`)

```yaml
name: Deploy to GitHub Pages
on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run lint
      - run: npm run test:run
      - run: npm run build
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: dist

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - id: deployment
        uses: actions/deploy-pages@v4
```

Перед тим як комітити, перевір актуальні мажорні версії actions у [starter workflow для static Pages](https://github.com/actions/starter-workflows/tree/main/pages).

**3. Налаштування репозиторію** (один раз)

1. Репозиторій має бути **public** (Pages на Free-плані). Перед цим перевірити, що в історії немає секретів. `.claude/settings.local.json` треба додати в `.gitignore`.
2. Settings → Pages → Build and deployment → Source: **GitHub Actions**.
3. Перший push або ручний запуск workflow → сайт на `https://romanhrytsko.github.io/daybowl/`.

**4. Оновлення застосунку**

- `registerType: 'autoUpdate'` — новий service worker підхоплюється при наступному відкритті. Дані в IndexedDB при цьому не змінюються.
- У Налаштуваннях показувати версію збірки: `define: { __APP_VERSION__: JSON.stringify(<git sha>) }` у Vite, `GITHUB_SHA` у CI. Так видно, що оновлення дійшло.

**5. Розробка паралельно з використанням**

- `localhost:5173` — окреме сховище, тому експерименти не зачіпають справжні дані. Щоб тестувати на реальних даних: експорт на Pages → імпорт локально.
- Нові функції робити в гілках; мердж у `main` = реліз.

**Критерії приймання фази 1**

- [ ] Push у `main` за кілька хвилин публікує сайт; падіння тесту блокує деплой.
- [ ] `https://romanhrytsko.github.io/daybowl/` відкривається, немає 404 на скрипти, іконки чи manifest; пряме посилання `#/day/2026-11-25` працює.

- [ ] Новий деплой не зачіпає даних; у Налаштуваннях видно нову версію.
- [ ] У Налаштуваннях видно «Сховище: постійне» (у встановленому застосунку) і дату останньої копії.

**Відкрите питання**

- Чи будеш користуватися з телефона? Якщо так, фаза 2 стає потрібною, бо інакше дані на пристроях розійдуться.
